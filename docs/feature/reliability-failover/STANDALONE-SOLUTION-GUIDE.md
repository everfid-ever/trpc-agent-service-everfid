# 企微 AI Bot 多租户可靠性平台 — 方案说明书

> **这是一份可独立分发的文档。** 阅读本文不需要代码仓库、部署文件或企业微信账号。它完整解释三个已实现能力的业务背景、设计选择、运行机制、故障过程与验收标准：
>
> 1. 节点故障后，两个租户仍能在原会话继续对话；
> 2. 消息正在处理或发送时节点故障，系统自动接管原消息；
> 3. 同一台主机上两个应用实例共存、单实例故障与重新加入后仍稳定。
>
> 若读者还需要核对实际实现，可按需查阅三个交付包中的 `CODE-APPENDIX.md`；本文本身不依赖这些代码附录。

## 平台定位（先读这一小节）

本平台是**企业微信侧 AI Bot 服务的多租户可靠性层**。需要先分清两件事，否则容易误解这套方案在保护什么：

| | 是什么 | 谁负责 |
|---|---|---|
| **Bot 的能力** | 对话推理、工具调用、技能、知识检索、记忆、产物生成 | Bot 自身的业务实现 |
| **Bot 的可靠性** | 上述能力在**节点故障**下不被破坏：消息不丢、用户不用重发、租户不串、结果不重复 | **本文档描述的平台** |

换句话说：本文不讨论"Bot 答得好不好"，只讨论"**Bot 挂了一个实例之后，还能不能把这个用户在这条会话里的第二轮问答正确完成**"。被保护的对象是一台带模型、工具、技能、知识、记忆与产物的智能体，而不是一个消息转发接口——正因如此，方案里才会同时出现"模型可以重跑但不能重复交付""工具副作用必须幂等""知识与记忆不得串租户"这三类看似无关的约束。

**一句话记住：** 模型可重跑、任务可重试，但**一次有效交付**与**租户边界**不可破。

## 一、用一句话理解这套方案

系统把一条企业微信消息拆成“可信归属、可靠接收、可接管执行、原子结果提交、可恢复投递”五个阶段。每个阶段都把必要事实保存到共享的持久化存储；因此应用节点只是可替换的执行者。一个节点消失后，另一个节点可以从最后一个已确认的事实继续，而不会猜测、串租户或让旧节点覆盖新结果。

这不是单纯的“重试机制”，而是一套**状态边界与所有权边界**：

```text
谁的消息？       → 经验证的 Bot 绑定决定
消息收到没有？     → 持久化 Inbox 决定
现在谁能处理？     → 租约决定
谁有权提交结果？   → 递增 fence 决定
回复是否已经发出？ → 投递台账决定
```

## 二、问题背景：为什么普通的单机聊天服务不够

假设平台有两个企业微信 Bot：

| Bot | 所属租户 | 会话中保存的内容 |
|---|---|---|
| Bot A | Tenant A | 用户在上一轮告诉它的代号 `ALPHA` |
| Bot B | Tenant B | 用户在上一轮告诉它的代号 `BRAVO` |

如果只有一个应用进程，进程退出后会产生四类典型问题：

1. **上下文丢失。** 代号只在内存里，重启后模型无法回忆。
2. **消息丢失。** 平台已经把消息交给服务，但服务尚未保存就崩溃。
3. **旧节点回魂。** N1 因网络隔离失去联系，N2 已经接管；N1 恢复网络后又把旧结果写回。
4. **回复重复。** 服务已经调用了下游发送接口，但在保存“发送完成”之前崩溃；新节点不知道用户是否已收到。

因此，“有两个容器”本身没有价值。真正需要回答的是：**每种事实保存在哪里、谁可以改变它、节点消失后由谁继续，以及不确定时系统如何诚实处理。**

## 三、核心概念：先建立共同语言

| 名词 | 通俗解释 | 在方案中的作用 |
|---|---|---|
| 租户（Tenant） | 一家企业或一组完全隔离的业务数据 | 决定配置、会话、工具、凭据和查询边界 |
| Bot 绑定（Binding） | “这个企业微信 Bot 属于哪个租户、如何验签和回复”的可信档案 | 让外部消息不能伪造租户归属 |
| Inbox | 已可靠接收原始消息的收件箱 | 证明消息不会因进程崩溃而丢失 |
| Outbox | 已产生但尚未投递到下一环节的待办清单 | 把数据库提交与异步消息发布解耦 |
| Stream | 可由多个执行者领取的工作队列 | 让未确认任务可以被其他节点领取 |
| Lease（租约） | 有过期时间的“临时处理许可证” | 决定此刻谁可处理同一会话 |
| Fence（栅栏号） | 每次接管都更大的序号 | 阻止失联旧节点迟到写回 |
| Terminal result | 一条消息已经得出最终业务结果的持久化事实 | 防止 P3 故障时重复跑模型 |
| Delivery Ledger | 回复发送状态台账 | 区分“未发、发送中、已发、不确定” |
| Reclaim（回收） | 把超时未确认的任务交给新执行者 | 节点故障后的自动接管动作 |

## 四、总体架构：哪些东西可以丢，哪些绝不能丢

```text
                         ┌──────────────────────────┐
                         │   统一企业微信回调入口    │
                         │  只选择健康的应用实例     │
                         └────────────┬─────────────┘
                                      │
             ┌────────────────────────┴────────────────────────┐
             │                                                 │
       ┌─────▼─────┐                                     ┌─────▼─────┐
       │ 应用 N1   │                                     │ 应用 N2   │
       │ 可被替换  │                                     │ 可被替换  │
       └─────┬─────┘                                     └─────┬─────┘
             └──────────────────┬──────────────────────────────┘
                                │
       ┌────────────────────────┼─────────────────────────┐
       │                        │                         │
┌──────▼──────┐        ┌────────▼────────┐       ┌────────▼────────┐
│ 持久化数据库 │        │ 工作流与协调服务 │       │ 外部企业微信服务 │
│ 业务权威事实 │        │ 队列、租约、心跳 │       │ 真实用户可见回复 │
└─────────────┘        └─────────────────┘       └─────────────────┘
```

### 4.1 持久化数据库保存什么

持久化数据库是唯一业务权威，至少保存：

- 每个 Bot 的可信绑定、所属租户和配置版本；
- 每条已经接收的原始消息；
- 会话的已提交上下文、输入顺序、最后一个有效 fence；
- 已完成的结果与待发送回复；
- 每条回复的投递台账和下游接受证据。

它的特点是：N1 和 N2 都能读取，N1 崩溃后事实仍存在，且关键写入可以在同一事务中提交。

### 4.2 队列与协调服务保存什么

队列与协调服务不是最终业务事实，而是用于提高吞吐和协调多节点：

- 工作队列记录哪些任务尚未被确认完成；
- 消费者标识记录哪个实例领取了任务；
- 租约记录某会话当前临时属于谁；
- 租约超时后，其他节点可以回收未完成任务。

即使队列或租约信息短暂丢失，数据库中的 `last fence`、会话版本和 terminal result 仍然会拒绝错误的旧写入。这就是为什么方案不会把协调服务当作唯一真相。

### 4.3 系统内部的"账本"一览（非代码读者版实现细节）

上两节说的"持久化数据库"和"队列与协调服务"，在实现里具体分成下面这些**账本**。你不需要记住表格名，只需知道**每个账本负责记住哪一件事、由谁写**：

| 账本职责（大白话） | 文档里的名字 | 谁来写 | 为什么必须有它 |
|---|---|---|---|
| **收到过什么** | `inbox`（收件箱） | 接收消息的节点 | 证明"消息确实到了系统"，并且在平台重复推送时只认一条 |
| **这条消息的处理任务** | `execution_record`（任务执行记录）、`preprocess_job`（待办事项单） | 接收 / 预处理节点 | 让"待处理的工作"能在另一个节点被重新发现 |
| **会话进度** | `session_head`（会话进度卡）、`session_commit`（结案记录） | 执行节点（结案时一次性写入） | 保证同一轮只结案一次，并记录接管权序号的最终值 |
| **对话历史（模型看到的那段对话）** | 官方会话后端的 `session_events`（每发生一件事就同步追加一条） | 执行节点（事件一产生就写，不等结案） | 这才是"接管后还能回忆起上下文"的来源；注意它与上面的平台表不是同一个表 |
| **工具执行是否生效（仅危险工具）** | `tool_attempt`（效果判定：未知/成功/失败）、`tool_result_payload`（加密后的工具返回值） | 执行节点 | 让接管者知道"这个工具到底有没有生效"，从而决定采用结果还是报告不确定，而不是盲目再跑一次 |
| **待发出去的事** | `outbox`（待发清单） | 结案时随结案一并写入 | 已得出结论但还没送达下一环节时，不丢事 |
| **回复发出去了吗** | `delivery_ledger`（投递台账） | 发送节点 | 区分"未发 / 发送中 / 已发 / 不确定"，避免重复发送 |
| **谁现在有权处理这个会话** | `lease`（临时处理许可，存在协调服务里） | 执行节点周期性续期 | 同一会话同一时刻只让一个节点处理 |
| **谁有权最终写入** | `fence`（接管权序号，协调服务与会话进度卡各存一份） | 每次拿到许可时递增 | 阻止"失联后又回来"的旧节点覆盖新结果 |

**一个重要的实现判断：** 这些账本里，**数据库里的那几本才是最终依据**；协调服务里的许可与序号只是"临时工牌"。工牌丢了可以重发，但数据库里的结案记录与接管序号不会被旧节点翻改。

### 4.4 几个关键时间参数的含义（非代码读者版）

故障发生后"多久能接手"由这几个时间决定。它们不是随手取的常数，而是**容错速度**与**误判风险**之间的取舍：

| 参数（通俗名） | 典型取值 | 通俗含义 | 调小 / 调大的代价 |
|---|---|---|---|
| **临时处理许可的有效期** | 30 秒 | 节点拿到"我负责这个会话"的许可后必须每 10 秒左右续期；停止续期后最多 30 秒，别人就能接手 | 调小 → 检测更快，但节点一卡顿就可能被误判丢失；调大 → 接手更慢 |
| **许可续期间隔** | 10 秒 | 心跳频率，必须明显小于有效期 | 必须小于有效期，否则会"自己以为还持有、其实已过期" |
| **超时任务回收扫描间隔** | 5 秒 | 存活节点每隔多久扫一次"有没有别人留下的、已过期的工作" | 调大 → 接手更慢；这是接管延迟的主要来源之一 |
| **待发回复的占用有效期** | 30 秒 | 某节点说"这条回复由我来发"之后若它挂了，最多 30 秒后别人可接管发送 | 与许可同理 |
| **入口健康探测间隔** | 1 秒 | 统一入口每隔多久问一次"你还活着且能干活吗" | 调太小会压垮后端；调太大会延长"新消息进不来"的窗口 |

> **为什么这些参数必须可记录、可调整，而不能写死在代码里？** 它们直接决定"故障后多久恢复"这一对外承诺。改动任何一个都必须重新测量恢复时间，不能沿用旧结论。
> **一个容易踩的坑：** 同一类参数在代码里往往还有一个"兜底默认值"，与部署实际生效的值**不同**（例如许可有效期兜底是 5 秒、部署实际是 30 秒）。对外结论必须引用**部署实际生效的值**，否则会得出差一个数量级的恢复时间。

## 五、能力一：故障后仍可在原会话继续对话

### 5.1 目标不是“能回复”，而是“回复正确的历史”

验收时，Bot A 和 Bot B 分别被告知不同测试代号。节点故障后，用户只问：

> 你属于哪个租户？我刚才告诉你的代号是什么？

问题中不再次提供代号。通过条件是：

- Bot A 只回答 Tenant A 和 `ALPHA`；
- Bot B 只回答 Tenant B 和 `BRAVO`；
- 两条消息仍进入各自原会话；
- 每个输入只出现一条最终可见回复；
- 服务端 tenant、session、任务和投递记录能够关联。

### 5.2 第一层：可信租户归属

外部请求中的 `tenant_id`、用户名或聊天标题都不可信。正确做法是：

```text
企业微信回调
  ↓
根据回调路由找到候选 Bot binding
  ↓
在该 binding 范围内验证签名与凭据
  ↓
验证成功后，binding 决定 tenant、Agent、凭据和配置版本
  ↓
才允许创建本次消息的 Tenant Context
```

因此，Tenant A 与 Tenant B 即使使用相同模型供应商，也不会共享会话、工具、知识、发送凭据或业务查询范围。模型上游 Key 是否相同不是隔离判据；**可信 binding 和持久化查询条件才是。**

### 5.3 第二层：原会话如何恢复

每个会话都由租户、Bot 绑定、外部用户和外部聊天等稳定身份组合得到。系统只把已经成功提交的对话轮次保存到会话历史中。

这样设计有两个理由：

1. 正在生成的半句话、失败工具调用或被取消的结果，不应该污染下一轮上下文；
2. N2 接管时只需读取数据库中的已提交历史，不需要从 N1 的内存搬运对象。

用户的下一条消息到达后，接管节点按照以下业务逻辑工作：

```text
找到可信 tenant 与 binding
  ↓
找到该 tenant 下的原会话
  ↓
读取已提交历史和下一输入序号
  ↓
执行新一轮任务
  ↓
将新结果、会话推进和待发送回复一起保存
```

这里“**一起保存**”非常重要：若只保存聊天历史却没有保存待发回复，节点在保存后、发送前故障时会让用户永远收不到结果；若先发送后保存，又会在重试时产生重复。

### 5.4 第三层：谁能处理同一会话

同一会话不能同时被 N1 和 N2 随意执行，否则两条消息可能交错写入。系统使用有期限的租约：

```text
N1 获得会话租约，按固定周期续约
    ↓
N1 健康：其他节点不能同时获得同一会话的租约
    ↓
N1 崩溃或与协调服务失联：它无法续约
    ↓
租约自然到期，N2 可以获得新的租约
```

租约解决的是“此刻谁在工作”，但还不足以处理网络隔离：N1 可能在租约过期后才恢复网络，并带着旧结果回来。因此每次成功取得租约都会获得一个更大的 **fence**。

### 5.5 第四层：fence 如何阻止旧节点覆盖新节点

```text
时间      N1                               N2                         数据库
─────     ─────────────────────────────    ───────────────────────    ─────────────
t1        获得 fence=11
t2        网络隔离，无法续约
t3                                         获得 fence=12
t4                                         提交最终结果               last fence=12
t5        网络恢复，尝试提交 fence=11                                拒绝旧 fence
```

数据库在写入会话结果时检查：提交者的 fence 是否不小于当前 `last fence`，输入序号和会话版本是否仍匹配。旧节点即使“还活着”、甚至模型已经算完，也不再有权改变结果。

这就是 **lease + fence** 的分工：

- lease 用于减少并发执行；
- fence 用于保证迟到者永远不能越权写入；
- 数据库是最后的裁决者。

### 5.6 故障后的完整业务时序

```text
1. N1 处理两个 Bot，已将会话历史保存到数据库
2. N2 启动，读取相同的 tenant/binding 配置和共享状态
3. N1 被非优雅终止，且不自动重启
4. N1 的租约停止续期，未确认队列任务成为可回收状态
5. N2 取得新的租约/fence，并接管可回收职责
6. 统一入口将新回调转给健康的 N2
7. N2 从持久化会话读取各自历史并完成新回复
8. N2 保存 terminal result 和投递台账，最终向正确 Bot 发送回复
```

## 六、能力二：在途任务接管与幂等投递

### 6.1 为什么“下一条消息正常”不能证明接管正确

一条新消息能被 N2 处理，只说明新链路可用；它不能证明 N1 崩溃时那条**已经被接收的原消息**没有丢失或重复。因此把消息生命周期明确划分为四个故障窗口。

```text
可靠接收 → 开始执行 → 已提交结果 → 下游已接受
    P1          P2          P3           P4
```

### 6.2 P1：已可靠接收，尚未执行

**场景：** 消息已经写入 Inbox 或可靠进入任务队列，但尚未真正开始执行。

**风险：** 接收节点崩溃后，消息被遗忘；或者任务被领取但永远不能再领取。

**方案：** 接收成功只在 Inbox 和必要 dispatch 信息持久化完成后才确认。N1 在这里崩溃时，N2 从 Inbox/待办清单或可回收队列发现同一原消息并继续处理。用户不需要重发。

**为什么这样做：** HTTP 或企业微信客户端显示“已发送”只代表网络传输完成，不代表服务端已经留下可恢复事实。

### 6.3 P2：模型或工具正在执行

**场景：** N1 已经领取任务并开始模型调用或工具调用，但还没有提交最终结果。

**风险：**

- N1 死亡导致原任务永远 pending；
- N2 接管后，N1 又恢复并提交旧结果；
- 模型或工具被调用超过一次。

**方案：** N1 不 ACK 原任务，直到 terminal result 已经持久化。节点失效后，N2 回收 pending 任务，获得更大的 fence，重新执行或继续可恢复步骤。N1 的旧 fence 不能提交。

**必须接受的事实：** 模型生成到一半的内部状态通常无法跨节点恢复，因此允许模型重新调用。这里追求的是**一次有效提交和一次业务效果**，不是“模型 API 绝不调用两次”。

**外部写操作怎么办：** 对每个写工具生成业务幂等键，例如“tenant + 原消息 + 业务操作”。外部系统成功创建资源后，持久化外部资源 ID；超时但不确定成功与否时进入待核对状态，不能盲目重试。

### 6.3.1 如果节点恰好是"工具执行到一半"挂掉的（最容易被误解的一问）

这是 P2 里最容易产生错误预期的地方，值得单独说清。

**问题：** Bot 正在执行一个工具调用（例如正在调外部系统、或跑一个几分钟的长任务），此时节点被强杀。这次工具执行的记录保住了吗？另一个节点接管后，会接着把没跑完的工具调用继续执行完吗？

**答案分两半：**

| 问 | 答 |
|---|---|
| "模型曾经请求调用哪个工具、参数是什么"保住了吗 | ✅ 保住了，而且是在工具**开始执行之前**就已经写进会话记录 |
| "工具已经执行到哪一步、产生了什么中间结果、外部系统是否已经改过"保住了吗 | ❌ **完全没有记录**。系统里没有任何地方保存工具的执行进度 |
| 接管后会"从断点接着跑"这个工具吗 | ❌ 不会。系统以**同一条用户输入重开一轮**：模型重新推理，并在历史中看到"上次那次调用没有拿到结果"的痕迹，由模型决定是直接回答还是**重新调用一次** |
| 用户需要重新发消息吗 | 不需要。输入本身是持久化的，重开一轮用的就是原消息 |
| 用户会不会看到两条回复 | 不会。最终只允许一次有效提交，用户可见回复仍是一条（下游去重边界见 §6.5） |
| 那外部系统会不会被写两次 | **可能。** 所以有副作用的工具必须自带业务幂等键——平台承诺的是"一次有效提交 + 一次可见回复"，不是"工具只执行一次" |

**唯一例外：需要人工确认的危险工具。** 这类工具（系统里叫"需确认/`ask` 策略"）多了一层记账：授权被消费时会留一条"效果未知"的记录，工具成功后把结果加密保存。若节点在工具执行中途挂掉，接管节点**不会重跑**，而是：读得到已保存的结果就采用它；读不到就以"这次工具效果不确定"结束并告警。宁可承认"不知道有没有生效"，也不盲目再来一次。

**为什么不做工具级续跑？** 因为工具的内部状态通常只存在于那个进程的内存里（甚至只存在于对方的服务器上）。要跨节点续跑，必须要求每个工具自己支持"查进度、从第 N 步继续"——这在通用平台上无法强制。因此正确的工程做法是：**把可恢复性下沉到工具的业务语义里（幂等键 + 可查询的资源 ID）**，而不是假装平台能恢复工具的内部执行。

**给长任务的现实预期：** 恢复的最小单位是"一轮输入"，不是"一次工具调用"。一轮里做了 20 次工具调用的长任务，接管后这 20 步都要重新推进，且已经发生的外部副作用不会自动回滚。需要工具级可恢复时，只有两条路：把它升级为需确认工具（获得"效果未知"账本 + 加密结果存储），或使用支持检查点的图式 Agent——但后者在当前实现里**同样救不了自动接管**：由于每次重跑都会开一条全新的"执行谱系"（lineage 取每次运行新生成的标识），检查点存储里查不到上一次的检查点；只有人工确认的续跑会明确指定"从哪个检查点继续"。**所以"工具级断点续跑"应当被理解为未实现，而不是尚未验证。**

### 6.4 P3：结果已经提交，最终回复还没发送

**场景：** 模型答案、会话推进和待发回复已经保存，但发送节点在调用企业微信接口前崩溃。

**正确做法：** 新节点只恢复“发布待发回复、领取发送任务、调用下游”的后半段，绝不重新执行模型。

**原因：** 结果已是权威事实。再跑模型可能得到另一份答案、产生额外费用，甚至调用写工具两次；从待发回复继续才能保持结果一致。

### 6.5 P4：下游已接受，但本地还没写入发送完成

**场景：** N1 已收到下游“接受回复”的证据，但在把 Delivery Ledger 标记为 `sent` 前崩溃。

**这是最难的窗口。** 新节点可能只知道“上一次发送调用没有完成本地确认”，却不知道用户是否已经看见消息。

投递台账至少使用以下状态：

| 状态 | 含义 | 新节点的行为 |
|---|---|---|
| `pending` | 从未发送 | 可直接领取并发送 |
| `sending` | 某节点正在请求下游 | 等待 claim 超时后接管 |
| `retry_wait` | 已知可重试失败 | 到达重试时间后再发送 |
| `sent` | 已持久化下游接受证据 | 只确认队列，不允许重发 |
| `ambiguous` | 无法判断下游是否已接受 | 查询下游、人工对账或按明确策略处理 |

如果下游支持稳定的客户端请求 ID 去重或查询，系统可以用该能力将 P4 收敛；如果协议没有这种能力，文档只能承诺**至少一次投递尝试**，不能承诺用户绝对只看到一条消息。这不是实现不足，而是分布式系统在“请求已发出、响应丢失”窗口中的客观限制。

### 6.6 为什么测试要有 P1–P4 暂停点

随机延迟或让模型“慢一点”不能证明故障恰好发生在目标边界。系统提供默认关闭的测试暂停点，测试时按以下步骤：

```text
1. 发送一条带唯一标记的原消息
2. 等待系统报告已命中 P1/P2/P3/P4 指定边界
3. 强杀真正承担该任务的节点
4. 保持受害节点停止
5. 只允许存活节点自然回收、续处理或重试
6. 检查同一原消息的最终结果、尝试次数、租户/会话和投递记录
7. 在重复观察窗口内检查迟到回复和重复业务效果
```

暂停点只延迟外部依赖响应或任务继续，不允许测试人员手工删除租约、重新入队、补发回复或修改任务状态。否则测试证明的是人工修复，而不是系统自动接管。

## 七、能力三：单主机双实例可用性

### 7.1 它解决的范围

本能力覆盖的是：同一台主机上，N1 和 N2 是独立应用进程或容器；N1 被强杀时，N2 在原入口下继续提供服务；N1 后续重新加入不会扰乱系统；再反向强杀 N2 也成立。

它**不**证明：宿主机断电、磁盘损坏、容器运行时故障或整机网络中断后仍可服务。因为这类故障可能同时影响 N1、N2、数据库和协调服务，属于跨主机高可用范围。

### 7.2 什么才算两个独立实例

| 必须隔离 | 可以共享 |
|---|---|
| 节点身份、进程启动身份、端口、消费者/owner 名称、临时目录、重启计数 | 镜像版本、配置版本、数据库、队列、协调服务、明确支持并发只读的资源 |

尤其重要的是 **进程启动身份**。同一个容器槽位重新启动后，必须生成新的身份。例如：

```text
第一次启动 N1：worker-node-a-start-101
N1 被强杀并重新加入：worker-node-a-start-205
```

如果两次身份相同，旧的 consumer、租约、日志或 delivery claim 很可能被误认为仍属于同一个执行者，使故障排查和接管判定失真。

### 7.3 为什么要有独立的统一入口

企业微信只应配置一个稳定公开地址。如果公开地址直接指向 N1，那么 N1 被杀时新消息无法进入，即使 N2 能处理队列积压也无法证明服务仍可用。

因此部署一个独立入口，它只做三件事：

1. 周期性检查 N1 和 N2 的业务 readiness，而不是只检查容器是否存在；
2. 只将企业微信 callback 转发给健康节点；
3. 当前端转发遇到连接失败、502、503 或 504 时，在返回前换用另一健康节点。

入口不是业务事实的存储者，也不负责 tenant 选择或消息去重；这些仍由后端的可信 binding 和 durable Inbox 完成。这样入口可以简单、可观测且易于替换。

### 7.4 readiness 和 liveness 的区别

| 检查 | 回答的问题 | 典型用途 |
|---|---|---|
| Liveness | 进程还活着吗？ | 判断是否彻底退出 |
| Readiness | 进程现在能安全处理业务吗？ | 统一入口是否应转发 callback |

一个进程可能还活着，但数据库断开、队列不可用、关键配置缺失或启动未完成。这种情况下它应当是 `live` 但 `not ready`，入口不能继续把用户消息发给它。

### 7.5 一次完整生命周期演练

```text
阶段 A：单实例基线
  N1 运行，两个 Bot 写入并回忆不同代号。

阶段 B：双实例基线
  N2 加入；两个实例健康、身份不同、无持续抢占或积压。

阶段 C：N1 非优雅故障
  禁用自动重启，强杀 N1，记录故障时刻；入口摘除 N1，N2 接管。

阶段 D：故障期间业务验证
  两个 Bot 在原会话发送新消息；检查 tenant、历史代号、唯一最终回复和服务端投递记录。

阶段 E：N1 重新加入
  显式启动 N1；确认新的 process identity，经过稳定窗口后无旧任务重发或连接振荡。

阶段 F：反向故障
  重建健康基线，强杀 N2，重复上述验证。
```

自动重启、优雅停机、共享数据库故障必须是不同子用例：

- **存活节点接管**：受害节点持续停止，证明 N2 自身接管；
- **自动恢复**：平台重建容器，验证重建时间，不能替代前者；
- **优雅停机**：验证停止接新任务、排空和退出，不能代替强杀；
- **依赖故障**：验证数据库、队列、协调服务不可用时的降级与数据一致性，不应预设持续服务。

### 7.6 重新加入：为什么必须换一个"身份"，而不是让旧进程复活

这是最容易被忽略、却直接决定验收真假的一点。

**先看一个反直觉的结论：** 被强杀的实例后来重新启动，**不能**算作"故障已自动恢复"。原因是这会混淆两个完全不同的机制：

| 机制 | 实际发生的事 | 能证明什么 |
|---|---|---|
| **存活实例接管** | 受害实例**一直停着**，另一个实例接手它的职责 | 系统真的有容错能力 |
| **自动重启 / 重建** | 平台把受害实例重新拉起来，它自己接着干 | 只是"重启了一下"，不能证明别人接得住 |

如果允许自动重启，强杀之后容器很快会被拉起来，"用户还能对话"这个现象既可能来自另一个实例接管，也可能来自它自己复活——**结论无法归因**。因此本方案在编排里显式关闭自动重启（`restart: "no"`），要求受害实例**保持停止**，并在此基础上验证接管。

**再看"重新加入"为什么必须换身份。** 每个实例有两个身份标记：

```text
部署槽位（固定不变）：      node-a / node-b      ← 表示"这是哪一个位置的实例"
本次进程身份（每次启动新）： 随机生成的一串字符     ← 表示"这是第几次启动的那个进程"
```

所有"谁在干活"的记录（临时处理许可、待发送任务的占用、日志、指标）都会带上这两个标记。设计上要求：**同一个槽位每次真正启动，必须生成新的进程身份。**

为什么？假设不换身份会发生什么：

```text
第一次启动 node-a：身份 = X
node-a 被强杀，另一个实例接管并完成了工作
node-a 被重新启动，如果身份仍是 X
   → 系统会把新启动的进程误认为"还是原来那个 X"
   → 原来 X 留下的、本应过期的许可和占用，可能被误认为仍然有效
   → 于是"谁接管了谁"变得无法追责，旧任务也可能被错误地重新执行
```

换身份之后，语义就清晰了：**重新加入的不是"原来那个执行者复活"，而是一个全新的执行者，从共享状态里观察到还剩什么工作、只接已经过期或明确可重试的部分。**

**验收时怎么确认这一点生效了？** 比对重新加入前后的"本次进程身份"：

- 若两个值**不同** → 说明身份已更新，符合设计；
- 若两个值**相同** → 🔴 这是严重问题，说明同一个位置的不同进程无法被区分，"是否真的接管过"也就无法证明。

这个检查不需要读代码：实例的状态接口会输出这两个身份标记，演练脚本会自动比对它们。

## 八、三个能力如何配合，而不是彼此替代

| 能力 | 回答的问题 | 不能替代什么 |
|---|---|---|
| 故障后继续对话 | 新消息能否在原 tenant/原会话正确处理 | 不能证明旧的在途消息已经完成 |
| 在途任务接管 | 原消息在不同持久化边界故障后是否自动完成 | 不能证明公开入口在节点故障时仍能接收新 callback |
| 单主机双实例 | 两实例生命周期、稳定入口和反向故障是否稳定 | 不能证明整机故障或跨故障域可用性 |

三者组合后的完整故事才是：**入口仍能收到新消息 → 正确路由到租户和会话 → 已接收旧任务可回收 → 新节点有唯一提交权 → 最终回复可恢复且可追踪。**

## 九、相关技术为什么这样选择

| 技术/机制 | 解决的问题 | 不能单独解决的问题 |
|---|---|---|
| PostgreSQL 事务 | 保存原子业务事实、会话版本、outbox、ledger | 不负责把任务主动分配给节点 |
| Redis Stream / 消费者组 | 多节点消费与 pending reclaim | 不阻止脑裂旧节点写数据库 |
| Redis Lease | 同一会话短时间内串行执行 | 不能防止过期 owner 的迟到提交 |
| Fence | 拒绝旧 owner 覆盖新结果 | 不负责检测节点是否死亡 |
| Transactional Outbox | 结果提交与异步发布之间不丢事实 | 不保证下游用户已看见消息 |
| Delivery Ledger | 发送状态、重试、接管与审计 | 无法凭空得知下游是否真的接受 |
| Health-aware Entry | 公开入口不随应用节点切换 | 不负责租户隔离和业务幂等 |
| 唯一 process identity | 重新加入后的所有者可追责 | 不替代 lease/fence 的状态正确性 |

这张表表达一个重要原则：**每项技术只解决自己擅长的一个边界，可靠性来自它们的组合，而不是把所有问题寄托在某一种中间件上。**

## 十、验收时应该收集什么证据

“看起来回复正常”不够。一次可审计的演练至少要关联：

| 证据类别 | 应记录的内容 |
|---|---|
| 版本与拓扑 | 提交版本、镜像、配置版本、N1/N2 身份、共享依赖 |
| 租户与会话 | tenant、binding、session、原消息、任务、回复的关联 ID（脱敏） |
| 故障动作 | 受害节点、强杀动作、故障时刻、受害节点始终停止的证明 |
| 接管过程 | 入口健康集合、连接所有者、worker/consumer、lease/fence、pending reclaim |
| 结果 | 原消息和新消息的最终回复、投递台账、重试次数、外部副作用幂等记录 |
| 时间 | 连接恢复、执行链路就绪、消息接收到最终可见回复的时间与采样误差 |

证据应保存在独立运行目录，不应混入本方案文档。方案文档定义“如何测、测什么、怎样判定”，运行目录保存“某一次实际执行的结果”。

## 十一、验收时必须分开说的三个数字（否则结论会错）

系统里存在三个看起来相似、含义完全不同的"次数"。把它们混为一谈，是这类项目最常见的验收误判。

| 数字 | 通俗解释 | 允许大于 1 吗 | 为什么 |
|---|---|---|---|
| **模型被调用了多少次** | 系统问了几次"AI 该回什么" | ✅ **允许** | 节点在执行中途挂掉时，"AI 想到一半"的状态保不下来，接管者只能重问一遍。这是分布式系统的客观事实，不是缺陷 |
| **任务被尝试了多少次** | 这条消息被处理（或重试）了几轮 | ✅ 允许，但**有上限** | 重试是为了最终成功；超过上限会转入"需人工处理"的明确状态，而不是无限重试 |
| **用户看到几条最终回复** | 聊天窗口里最终出现了几条答复 | ❌ **必须恰好 1 条** | 这是对用户的承诺，由"同一条回复只允许被标记一次已发送"的台账约束保证 |

**为什么必须分开说？** 因为它们对应三个不同的期望：

- 如果有人用"AI 只调用了 1 次"作为验收标准，那么**正确的容错行为反而会被判成失败**（接管时重问了一次）；而真正的风险——用户收到两条回复——却没被检查。
- 反过来，只看"用户收到 1 条"也不够：它可能是碰巧只发了一次，而不是系统保证了只发一次。

**正确的验收表述应该是：**

> 一次有效的最终结果提交 + 一次业务效果 + **用户无需重新发送** + 每个输入只产生**一条**可见最终回复。
> 同时如实记录：AI 被调用的次数**可以大于 1**，任务尝试次数在预设上限内。

**一句话记忆：** "AI 问了几次"是过程；"用户看到几条"是结果。过程允许重来，结果必须唯一。

> ⚠️ 与之配套的诚实边界：如果下游（企业微信侧）不具备"按请求标识去重或查询"的能力，那么在最棘手的"请求已发出、响应丢失"窗口里，系统只能保证**至少一次投递尝试**，不能承诺用户绝对只看到一条。这不是实现不足，而是该窗口的客观限制；系统会把这种情况标为"不确定"并告警，而不是假装成功。详见 §六 的 P4。

## 十二、明确的保证与边界

### 本方案保证

- 已持久接收的消息不会因单个应用节点故障而需要用户重新发送；
- 共享状态中的 tenant、会话和业务结果能够被存活节点读取；
- 同一会话的旧执行者不能用更小 fence 覆盖新执行者；
- 已提交结果不会因发送节点故障而重新跑模型；
- 多实例重新加入会以新的执行身份参与协调；
- 单主机单个应用实例故障下，稳定入口可将新 callback 转至健康实例。

### 本方案不夸大的内容

- 不承诺跨主机、整机断电、宿主机网络隔离下仍可服务；
- 不承诺模型调用次数恒为一次；P2 接管可能重跑模型；
- **不承诺工具级"断点续跑"**：工具执行进度不落库，接管后是"以原输入重开一轮"；有副作用的工具可能被执行两次（at-least-once），需要工具自带业务幂等键（见 §6.3.1）；
- 不承诺无法被下游去重或查询的 P4 场景仍能绝对恰好一次展示；
- 不把 Docker 自动重启视为存活节点接管；
- 不把健康检查、连接恢复或队列恢复单独当作完整业务恢复时间。

## 十三、交接时可直接使用的说明

> 系统以可信 Bot binding 建立 tenant 边界，用持久化 Inbox 保证消息可靠接收；任务经可回收队列分发，同一会话通过带过期时间的 lease 串行执行，并以递增 fence 阻止失联旧节点迟到提交。terminal result 与待发回复原子保存，Delivery Ledger 管理发送、重试和不确定投递。单主机部署两个独立实例，并通过独立健康探测入口维持同一 callback 地址；一个实例强杀后，另一个实例接管，重新加入以新的进程身份恢复，随后再验证反向故障。整个方案分别验证新消息连续性、原在途消息接管和双实例生命周期，不把它们混为一个结论。

这段描述既可以用于项目交接，也可以用于向非代码读者说明“系统为何能在节点故障后仍正确服务”。
