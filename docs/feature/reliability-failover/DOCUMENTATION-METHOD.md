# 可靠性文档方法：四级深度与二十个角度

本文档规定三个能力说明的阅读与审查方式。它不是抽象模板：每个能力目录的 `README.md` 都给出 L1–L4 文件地图，读者可据此定位每个问题的概念、机制、实现和验收材料。

## 四个深度级别

| 级别 | 回答什么 | 最低交付物 | 不能混淆的原因 |
|---|---|---|---|
| L1 概念级 | 做什么、保证什么、不保证什么 | 场景、承诺、边界、三类计数 | 只写机制会让读者把技术细节误当成业务承诺 |
| L2 机制级 | 靠什么做到、节点在故障瞬间如何变化 | 因果链、故障时序、“不能只做 X”的反例 | 只报组件名不能证明它们如何共同避免竞态 |
| L3 实现级 | 哪个 durable 键、表、函数、参数和启动顺序负责 | DDL、算法、接口、配置、代码地图 | 机制若没有精确落点，无法审查或复现 |
| L4 验收级 | 怎样证明、失败时怎样识别和处置 | 判定表、最小证据闭环、反例、演练/处置 | 单元测试通过不等于故障承诺已经被证明 |

同一命题在不同深度必须使用不同句子。例如“用户只看到一条回复”：L1 是带下游去重边界的承诺；L2 是 terminal commit、Outbox、Ledger 的分工；L3 是 reply segment 的 Ledger claim 和 `sent` 状态条件更新；L4 是 provider 不可去重时只允许得到 `ambiguous` 的反例与告警处置。

## 二十个审查角度

下表是所有能力都必须回答的通用判据。“为什么必须有”说明缺失时的典型错误；“提问式判据”是评审时应能得到明确答案的问题。各能力的具体位置由其 `README.md` 文档地图和各级标题给出。

| 编号 | 角度 | 为什么必须有（缺失会犯什么错） | 提问式判据 |
|---|---|---|---|
| A1 | 保证等级 | 把 best effort 说成绝对保证 | 在什么前提、什么故障域内，系统究竟保证什么？ |
| A2 | 保护对象 | 只保护 HTTP 请求而遗漏会话/副作用/回复 | 被保护的是输入、会话、工具效果、回复，还是其中一部分？ |
| A3 | 计数语义 | 将模型重试误判为用户重复回复 | 模型调用、任务尝试、业务效果、可见回复分别如何计数？ |
| A4 | 粒度与术语 | tenant、Bot、session、request 被混为同一 ID | 每个主键/术语的边界和一对多关系是什么？ |
| A5 | 故障对象清单 | 只考虑进程退出，遗漏网络、渠道或共享依赖 | 哪些组件可能失效，哪些仍假定可用？ |
| A6 | 故障窗口划分 | 在“调用已发出、结果未落库”等窗口做错误重试 | 每一步 durable 边界在哪里，任一边界前后故障分别怎样处理？ |
| A7 | 假设与不可测项 | 对外部系统的未知状态做虚假判断 | 哪些状态无法从本系统观测，无法观测时如何收敛？ |
| A8 | 判定真死 | 因短暂抖动发生双 owner | 何时 lease 失效、何时入口摘除、何时允许另一 owner 接管？ |
| A9 | 权威状态与数据模型 | 把缓存/日志误用作恢复事实 | 恢复时读取哪张表/哪个键，谁有权写它？ |
| A10 | 状态机与生命周期 | 状态跳转遗漏终态或回退路径 | 合法状态、终态、可重试状态以及转移条件是什么？ |
| A11 | 顺序即策略 | 先发消息再落状态或先消费令牌再无恢复记录 | 哪些写入必须先于外部调用/ACK/提交？ |
| A12 | 并发控制 | 两个节点同时提交或完成同一操作 | 哪个 lease、version、fence 或 CAS 使旧 owner 失效？ |
| A13 | 幂等与去重边界 | 把内部 exactly-once 延伸到不可控的下游 | 哪层去重，使用什么幂等键；下游不支持时承诺降级为什么？ |
| A14 | 恢复动作判定 | 对有副作用的操作盲目重放 | 哪些状态重跑、查询、复用结果、告警或终止？ |
| A15 | 租户隔离强制点 | 依赖调用方“记得带 tenant”导致串租户 | tenant 在入口、查询、密钥、会话和回复各如何被强制绑定？ |
| A16 | 身份与授权 | 未验证的用户输入选择了 Bot/tenant/工具 | 谁证明渠道身份，谁能领取/确认/发送/恢复？ |
| A17 | 观测与证据 | 只能说“看起来恢复了” | 需要哪些 request/fence/owner/ledger/provider 证据才能闭环？ |
| A18 | 时间口径与容量 | TTL、重试和积压导致错误 RTO 预期 | TTL、renew、reclaim、退避、尝试上限及积压影响是什么？ |
| A19 | 不承诺清单 | 将同机 HA 误读成跨机容灾 | 哪些故障域、下游能力或工具类别明确不在承诺内？ |
| A20 | 变更与演练 | 配置/迁移变更破坏不变量却未被发现 | 上线前需要哪些迁移、兼容性检查、故障演练和回滚证据？ |

### 位置索引（每个能力目录均适用）

下表补足“文档位置”这一强制判据。`{能力目录}` 分别替换为 `conversation-continuity`、`inflight-task-takeover` 或 `single-host-multicontainer`；同一角度必须在列出的文件中得到与该级别相称的回答，不能只在某一篇出现。

| 角度 | 文档位置 | 应落下的结论 |
|---|---|---|
| A1–A4 | `{能力目录}/OVERVIEW.md`；机制/实现涉及计数时同步至 `FULL-GUIDE.md`、`REFERENCE-IMPLEMENTATION.md` | 承诺、对象、模型/任务/回复计数和术语边界 |
| A5–A8 | `{能力目录}/FULL-GUIDE.md`、`design.md`；运行参数同步至 `release-and-operations.md` | 故障域、窗口、不可测状态、死亡/接管判定 |
| A9–A14 | `{能力目录}/design.md`、`implementation-walkthrough.md`、`CODE-APPENDIX.md`、`REFERENCE-IMPLEMENTATION.md` | 权威记录、状态机、顺序、lease/fence/CAS、幂等键及恢复算法 |
| A15–A16 | `{能力目录}/OVERVIEW.md`、`design.md`、`REFERENCE-IMPLEMENTATION.md` | tenant/binding/session 强制点与渠道、控制面、执行权授权 |
| A17–A18 | `{能力目录}/testing-and-acceptance.md`、`release-and-operations.md` | 证据字段、判定表、TTL/重试/容量和告警口径 |
| A19–A20 | `{能力目录}/OVERVIEW.md`、`testing-and-acceptance.md`、`release-and-operations.md` | 不承诺的故障域、反例、迁移/发布/回滚和演练门禁 |

## 阅读顺序

先读目标能力的 L1，确认承诺没有被夸大；再读 L2，检查机制是否覆盖对应故障窗口；随后用 L3 对照真实迁移和代码；最后用 L4 的证据闭环和反例验证。任何结论都应能从 L1 追到 L4，或从一次演练的证据反查到其 L3 条件更新。
